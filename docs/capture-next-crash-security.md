# Capture Next Crash and the elevation boundary

## Product scope

System contains an explicit, preview-first Capture Next Crash workflow. It configures future Windows Error Reporting (WER) capture; it does not crash an application, capture a running process, debug a process, analyze memory, or change diagnostic confidence. Configuration active does not mean a dump has been captured.

The supported target is an ASCII executable basename (letters, digits, dot, underscore, hyphen; 5–128 characters; `.exe` suffix; no leading dot or consecutive dots). Identity is case-normalized and name-based, not a full path or signer identity. All applications with the same basename in the selected native scope are affected machine-wide. The user must confirm a desktop application matching the OS architecture. Services, application hangs, custom crash reporters, automatic-debugger configurations, and WOW64 applications on a 64-bit OS are outside the capture guarantee. Microsoft documents a separate WOW64 configuration; this release deliberately does not modify a second registry view.

## Windows policy and location

Only `HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps\<app.exe>` in the OS-native registry view is writable: Registry64 on 64-bit Windows, Registry32 on 32-bit Windows. The process's own bitness does not choose the view. Global/default LocalDumps values are never modified. Absent application values inherit Windows/global behavior; an absent value is displayed as absent, not as an invented effective default.

The fixed policy is `DumpType = 1` (REG_DWORD mini dump), `DumpCount = 3` (REG_DWORD), `DumpFolder = %LOCALAPPDATA%\FaultWitness\Captures` (REG_EXPAND_SZ). Full dumps are not requested automatically: they expose substantially more memory and consume more space. Mini dumps are smaller but can still contain credentials, documents or other private process memory and may be insufficient for an investigation. There is no reliable universal size estimate and the count is not a byte quota. The target process must be able to write within its own local profile. The ordinary desktop process creates its own capture directory; the helper never creates folders or grants ACLs. Other accounts/services, sandboxes and restricted tokens may not have usable access. The scanner discovers file metadata under the current user's capture directory using existing crash-artifact semantics.

WER rotates dumps according to DumpCount; this is not an aggregate disk quota across applications/profiles. FaultWitness does not delete dumps. Restore ends this policy but keeps existing artifacts. Users can remove reviewed capture files manually in their local FaultWitness Captures directory. No unrelated Windows CrashDumps files are cleaned up. Disabling or restoring configuration is the deliberate way to stop further growth; no retention worker or background polling is added.

## Existing state and restore

Supported prior values preserve exact absence and DWORD values: DumpType absent/1/2; DumpCount absent/1–10; DumpFolder absent or REG_EXPAND_SZ with exactly the fixed capture token or `%LOCALAPPDATA%\CrashDumps`. A custom folder, custom dump type, wrong registry value kind, out-of-range value, or nested subkey makes configuration unsupported and read-only. Private unsupported folder text is not persisted. This restriction intentionally prevents forged restore requests from becoming arbitrary privileged dump-location commands.

Unrelated values remain untouched and are included in a typed SHA256 fingerprint for compare-before-write. Restore recreates prior supported values and absence; it deletes an app key only if originally absent and now empty, never recursively. An originally empty key remains present. External changes to supported values or the unrelated fingerprint block stale operations. A later unreverted local journal action also blocks restoring an older action. The bounded mutex serializes helper instances, including across sessions; contention or inaccessible mutexes fail closed. This is not a registry transaction against arbitrary administrator tools: a narrow race after the last comparison, changes that return to identical bytes (ABA), OS failure and external administrators cannot be excluded. Readback and conservative partial-write rollback reduce these risks without pretending the registry has compare-and-swap semantics.

## Existing helper audit and replacement

The previous helper accepted `enable-local-dumps` / `restore-local-dumps` command-line arguments. It had basename filtering but silently chose defaults, accepted additional arguments, performed no expected-state check, journal or readback, and restore recursively deleted the application key. There was no IPC endpoint or caller authentication. Those commands and recursive deletion are removed.

The helper accepts exactly one bounded base64 JSON request, schema 1, with action GUID, semantic operation, target basename, short-lived creation time, expected state and desired state. It rejects unknown/missing/duplicate properties at both request and nested-state levels. Allowed operations are only `ConfigureApplicationCrashDump` and `RestoreApplicationCrashDumpConfiguration`. Configure requires the exact fixed policy; restore requires current fixed policy and a supported prior state. Registry paths and value names are internal constants. There is no registry-path parameter, generic registry editor, file path/result file, shell, PowerShell, process/service/environment command, persistent server, socket, or named-pipe endpoint.

Each helper process requires administrator consent through its manifest/UAC. The desktop launches the absolute adjacent helper executable, never PATH search, and passes only a base64 argument. Its structured result is carried in a bounded process exit word (status, automatic rollback flags and low 16-bit Windows error); actual state is independently reread by the desktop. No raw exceptions are shown. The helper exits after one operation.

Caller origin is **not authenticated** by command-line knowledge or executable proximity. A hostile process can invoke the helper and cause a UAC prompt; it cannot use an already running privileged generic channel. Security rests on per-invocation administrator consent and helper-side validation even for malicious callers. Same-user executable/database tampering and a user accepting a replaced unsigned development binary are not solved by this protocol. Production distribution should use signed binaries in an administrator-protected installation directory. Existing HKLM ACLs must retain their Windows administrator protection. No claim of tamper-proof or cryptographically authenticated journal/provenance is made. A same-user process can deny service by damaging the journal; it cannot make the helper write outside the allowlist.

## Journal and transaction

Schema version 3 adds a dedicated structured `crash_capture_actions` SQLite table, preserving scans, incidents, settings and the legacy journal table. Columns include action/operation/target/time/elevation/version, exact previous/requested/observed supported values and key presence, unrelated-state fingerprint, result, rollback availability/status and safe native error. History clearing does not erase recovery records. Pending/recoverable/unresolved failures are retained; old terminal records are pruned with a 90-day and recent-500 policy. Reads are bounded and favor recoverable actions; malformed rows are skipped. SQLite remains local and user-writable.

Flow: read preview; explicit user confirmation; durable pending intent; UAC; independent helper validation and expected-state comparison; apply; readback; result return; independent desktop readback; durable final status. A failed intent save prevents dispatch. Cancellation of UAC is journaled. Once dispatch starts, the application does not kill a helper midway through its writes. If the application exits or the final journal save fails, pending remains unverified. On reopening, a pending configure can be reviewed for recovery and restored only when the actual state matches its requested policy. It is never relabeled successful just because an intent exists.

Partial failures cause conservative rollback only while each owned field still matches a before/desired transition and unrelated state is unchanged. Drift blocks automatic rollback. Failures remain visible; success always requires verification. Restore has its own pending and completed action, then marks the original rollback complete. An interruption between those records cannot authorize a blind write because restore checks current registry state again.

## Privacy and performance

Dumps stay local. No upload, telemetry or cloud analysis is added. Journals contain configuration tokens, never dump bytes or profile paths. Normal JSON/support exports do not open referenced artifact files or recurse through capture directories. Crash-artifact raw data and non-metadata fields are excluded even with raw-event export enabled. Support ZIP contains only its existing summary and sanitized event JSON. Dump extensions are ignored by Git; all tests use synthetic state or sentinel text in temporary directories.

Readiness/scans never write configuration. State is read on relevant page activation, explicit preview/refresh, and action completion; no capture polling is added. Normal scans add only the existing metadata-discovery traversal for the controlled capture directory. Rules are unchanged.

## Sources and validation boundary

- [Microsoft: collecting user-mode dumps](https://learn.microsoft.com/en-us/windows/win32/wer/collecting-user-mode-dumps) — value kinds, global/application inheritance, ACLs, dump types/count, custom reporters and automatic debugging limitations.
- [Microsoft: application/service crash troubleshooting](https://learn.microsoft.com/en-us/troubleshoot/windows-server/performance/troubleshoot-application-service-crashing-behavior) — separate WOW64 settings for 32-bit applications.
- [Microsoft: registry keys affected by WOW64](https://learn.microsoft.com/en-us/windows/win32/winprog64/shared-registry-keys) and [alternate registry view](https://learn.microsoft.com/en-us/windows/win32/winprog64/accessing-an-alternate-registry-view) — explicit native-view selection instead of process-bitness assumptions.

Development validation uses synthetic registry adapters, the actual helper protocol validator/engine, SQLite migrations, UI workflow/headless rendering and export regressions. No real application is crashed and no development-machine registry write or real dump is needed. Real UAC/Windows WER end-to-end validation remains a disposable-VM release check; synthetic verification does not prove a future application will generate a dump.
